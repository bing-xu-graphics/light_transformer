# Procedural scene generation

Our indoor training scenes were generated from [Infinigen](https://github.com/princeton-vl/infinigen). Development used version `v1.12.1` and our public [project fork](https://github.com/Galaxeaaa/infinigen), which records the generation experiments used by the project.

We do not redistribute Infinigen source code or modified upstream files here. Install it separately using its upstream instructions. The downloadable teaser scene is generated output and includes the upstream BSD 3-Clause license notice.

## Storage planning

Raw scenes typically occupy about 500 MB to 2 GB each. A 14,000-scene dataset therefore requires roughly 7 to 28 TB for source scenes alone, before rendered outputs, processed arrays, logs, and temporary files. Prepare sufficient cluster storage or local SSD capacity before launching large generation runs, and leave working space for failed, interrupted, and repeated jobs.

## What we changed in the workflow

The project gradually narrowed generation toward single indoor rooms that were practical for light-transport training. The project fork records controls for:

- selecting a supported room type, such as a living room or bathroom
- generating one room per floor plan
- hiding rooms outside the selected room
- disabling terrain, skirting boards, ceiling skirting, and pillars
- suppressing unnecessary ground-truth views during coarse generation
- using fixed room contours and controlled room dimensions
- running multiple seeds through the job manager

These changes are documented by the fork's [`generate_ltm.md`](https://github.com/Galaxeaaa/infinigen/blob/main/generate_ltm.md). Use that file as the record of the commands used for the original dataset. The fork itself is not a dependency of this repository.

## Outputs used by this project

For each successful seed, we retained the coarse Blender scene:

```text
dataset-*/<seed>/coarse/scene.blend
```

The generation job writes `finished_seeds.txt` and `crashed_seeds.txt`. We used those manifests to collect successful `scene.blend` files before conversion.

## Blender and PBRT export

We used [io_scene_pbrt](https://github.com/stig-atle/io_scene_pbrt) as the basis for exporting Blender scenes to PBRT. The original project workflow modified exporter code for dataset preparation, so it must retain the upstream attribution and GPL terms when released.

The exporter targets an older PBRT workflow. Verify exporter compatibility on a small scene before processing a full dataset.

The paper workflow combined generator controls with a project Blender-to-PBRT exporter. Exterior rooms were suppressed during generation through `hide_other_rooms_enabled=True`, with terrain, skirting boards, and pillars disabled by the command recorded in [`generate_ltm.md`](https://github.com/Galaxeaaa/infinigen/blob/main/generate_ltm.md).

The original development history also contains the actual conversion scripts. They flatten object parenting, remove generator placeholders, triangulate meshes, realize geometry-node instances, apply and simplify modifiers, skip objects whose names end in `exterior`, assign randomized diffuse reflectance, place a rectangular area light beneath the ceiling, export PLY meshes and PBRT v3, upgrade to PBRT v4, and render a preview. Those scripts include upstream-derived portions and hard-coded development paths, so this repository documents their behavior instead of presenting a newly rewritten replacement as original project code.

## Important: validate surface normals

We discovered after the paper training runs that some surfaces generated by Infinigen had inherently flipped normals. These caused black areas in some rendered training samples and reduced data quality.

For newly generated scenes, fix this in Blender before PBRT export:

1. Enable **Face Orientation** and inspect every retained room and object.
2. Recalculate normals outside or inside as appropriate for the surface. Interior walls may require a different orientation from closed objects, so do not apply one rule blindly to the entire scene.
3. Manually flip any remaining incorrect faces.
4. Export a small validation scene and verify the exported geometric and shading normals before launching large rendering jobs.

This correction is not part of the original paper results. We expect corrected normals to substantially improve the training data and likely improve training quality.

## Extending the generator

The core development behind this project was completed by May 2025, before LLMs and coding agents became as capable as they are today. The original scripts document our process, but they are not the limit of what can be built now. We encourage using coding agents and Blender MCP to automate normal checks, validate materials and lights, organize scene structure, and expand the diversity of generated scenes.

The source scene representation and renderer interface are also replaceable. Feel free to use another renderer or scene format, then convert its outputs to the model-ready arrays described in [`../example_scenes/README.md`](../example_scenes/README.md).

## Reproducibility notes

The original dataset was generated across changing scene configurations. Seeds alone are not enough to reconstruct every training scene unless the generator revision and command-line overrides are also recorded. The included test set therefore provides processed model inputs and reference outputs rather than claiming exact regeneration from a seed.
